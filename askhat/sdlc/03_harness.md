# Часть 3. AI Harness — из чего состоит и как устроен

> В Части 2 мы видели, что главное преимущество — в накоплении общей памяти через маховик. Эта часть отвечает на вопрос: **где конкретно эта память живёт и из чего состоит**.
>
> Читается за 12 минут.

---

## 1. Что такое harness

**Harness — это не команда, не процесс и не инструмент. Это среда.**

Конкретно: набор файлов, правил и базы знаний в репозитории организации, через который **команды и AI-агенты работают по общим правилам**.

Аналогия из обычной IT: операционная система. Её не запускают как отдельную программу — она просто *есть* и предоставляет общую среду, в которой запускаются программы. Все приложения опираются на её API, используют её файловую систему, следуют её соглашениям.

Так же и harness — это «операционная система для AI-разработки» в организации. Команды работают внутри неё, AI-агенты получают через неё контекст, изменения накапливаются.

**Что физически в репозитории**:
- Файлы с правилами (`AGENTS.md`, `CLAUDE.md` и подобные)
- Папка с базой знаний организации
- Шаблоны (для спек, для PR, для retrospective)
- Конфигурация для AI-агентов (промпты, инструменты, правила)
- Журналы решений
- Скрипты автоматических проверок

Это всё под контролем версий и ревьюится как обычный код.

---

## 2. Зачем harness нужен

Часть 2 показала на примере: AI **без shared memory** переизобретает в каждой сессии — у каждого человека и у одного человека во времени. Harness — это и есть та самая shared memory, плюс правила работы с ней.

Совсем коротко: **harness нужен, чтобы то, что выучила команда, не терялось и применялось AI автоматически.**

---

## 3. Главная идея — слоистая природа

Harness — это **два слоя**, и важно их различать:

```
┌─────────────────────────────────────┐
│  Слой организации (org layer)       │  ← это мы строим
│  — База знаний, шаблоны, правила,    │
│    стандарты под нашу специфику      │
├─────────────────────────────────────┤
│  Слой инструментов (baseline)        │  ← это даёт индустрия
│  — Plan Mode, AGENTS.md, indexing,   │
│    subagents, hooks, MCP             │
└─────────────────────────────────────┘
```

Эта граница не статична. То, что было нашим org layer год назад, сегодня **встроено** в инструменты как baseline. Через год часть нашего сегодняшнего org layer тоже там окажется.

### 3.1 Слой инструментов (baseline)

Что приходит из коробки от современных AI-платформ для разработки. Сегодня это (примерный список — конкретное наполнение меняется):

- **Plan Mode** — агент сначала составляет план, потом действует
- **Понимание `AGENTS.md` / `CLAUDE.md`** — стандарт инструкций для агента, который читают все основные tools
- **Индексирование репозитория** — агент видит код целиком, может ориентироваться
- **Subagents и параллельные сессии** — несколько агентов на разных частях работы
- **Hooks и event triggers** — реакции на события (file save, file create)
- **Code review** — встроенные возможности AI-проверки кода
- **MCP-интеграции** — стандарт подключения внешних tools

Эти штуки **не нужно строить** — они уже есть в Claude / Cursor / Copilot / Windsurf и других. Методика **полагается** на них и не дублирует.

Один из принципов методики (см. Часть 1): по мере того, как baseline растёт, методика **сжимается**. Если завтра в Cursor встроят полноценное «Knowledge Base management» — мы уберём этот элемент из org layer.

### 3.2 Слой организации (org layer)

Что строится **сверху** baseline и составляет «наш harness». Это территория, которую baseline пока не покрывает.

Главные элементы:

**База знаний (Knowledge Base, KB)**
Структурированное хранилище паттернов, решений, стандартов организации. Что у нас за продукт, какая архитектура, какой стек, какие conventions. Растёт со временем — каждая фича добавляет в неё что-то.
*Зачем*: чтобы AI имел контекст, а не отвечал generic советами.

**Таблица типов задач (Task-Type Matrix)**
Описание, какие у нашего продукта бывают типы задач и какой режим работы AI для каждого. Например: «email-уведомление» — AI делает сам по KB, человек получает уведомление; «изменение auth-flow» — AI готовит план, человек утверждает.
*Зачем*: чтобы автономия AI настраивалась под риск задачи, а не была одинаковой для всего.

**Журнал решений (Decision Log)**
Записи о значимых решениях: что выбрали, почему, какие альтернативы отвергли. Особенно ценны записи «почему отклонили предложение AI».
*Зачем*: чтобы знания о причинах не терялись с людьми; чтобы AI потом мог использовать это как обучающий материал.

**Проверка на выходе (Integration Gate)**
Механизм, который перед deploy проверяет: спека актуальна? тесты прошли? стандарты соблюдены? Если нет — блокирует merge.
*Зачем*: чтобы маховик не деградировал, чтобы каждый цикл оставлял правильные артефакты.

**Интерфейс команды (Team API)**
Публичное описание команды для других: чем занимается, как с ней работать, какой SLA. Читается и людьми, и AI-агентами других команд.
*Зачем*: чтобы межкомандная координация не требовала митингов на каждый запрос.

**Стандарты**
Design system, copy guidelines, security policies, accessibility rules, code conventions. Всё, что говорит «вот так у нас принято».
*Зачем*: чтобы AI генерировал код в стиле организации сразу, а не приходилось каждый раз объяснять.

Эти элементы — главные. Детали каждого — в Части 4.

## 4. Как это работает в потоке

Современные AI-инструменты (Claude Code, Cursor и подобные) **сами умеют**: разбивать запрос на шаги, читать AGENTS.md и базу знаний, применять правила, отслеживать зависимости между изменениями, идти по плану до конца. Это уже встроенный функционал — *baseline*.

**Поэтому методика не описывает «процесс прохождения задачи через harness» отдельно.** Этот процесс живёт в инструменте.

Методика обеспечивает только две вещи на границах:

**На входе** — у AI-агента есть правильный контекст:
- AGENTS.md / правила
- Релевантные паттерны из KB
- Спека или формулировка интента
- Информация о blast radius и нужных gates

**На выходе** — Integration Gate проверяет, что цикл оставил правильные артефакты:
- Спека актуальна
- Тесты прошли
- KB пополнена тем, что узналось
- Decision Log имеет записи по значимым решениям

Что происходит **между** входом и выходом — территория инструмента. По мере того, как baseline растёт, методика будет описывать всё меньше «как» и всё больше «что должно быть в результате».

## 5. Чем harness отличается от обычной документации

Внешне harness может выглядеть как просто «папка с документами». Принципиальные отличия:

**Накопительный (flywheel).** Документацию пишут отдельно от работы. Harness — **побочный продукт самой работы**: каждая задача наполняет KB и Decision Log по ходу. Если правильно устроен — пополняется без отдельного «документационного спринта».

**Читается AI, не только людьми.** Документация пишется для людей — AI её парсит лосс­но. Harness специально устроен так, чтобы AI-агент мог взять оттуда паттерн и применить, проверить соответствие правилу, вывести действие. На практике это обычно Markdown с YAML frontmatter (для людей плюс метаданные для машин).

**Общий + локальный.** В большой организации главный harness — **общий** (стандарты, baseline-правила, KB). Поверх возможны локальные нюансы — специфика отдельной части продукта. Локальные нюансы наследуют общие правила, не противоречат им. Детали — в одной из следующих частей.

---

Помимо этих свойств harness, конечно, наследует **общие принципы методики** из Части 1: outcomes-not-processes, эволюция вместе с инструментами, оптимизация под человека-bottleneck, education-as-part-of-methodology. Здесь не повторяемся — это применяется и к harness тоже.

---

## 6. Что НЕ относится к harness

Чтобы избежать путаницы:

- **Это не система для замены людей.** Harness — среда; решения принимают люди. AI работает быстрее в этой среде, но не замещает суждение.

- **Это не работает без активной поддержки.** Harness нужно вести, обновлять, чистить от устаревшего. Кто это делает — отдельный вопрос (вернёмся в следующих частях). Без поддержки harness становится мёртвой документацией за 2-3 месяца.

- **Это не «универсальная методика».** Harness даёт **shape** — какие элементы должны быть, как они организованы, как взаимодействуют. **Содержимое** каждый раз заполняется под организацию: ваш стек, ваши паттерны, ваши стандарты. У платёжной системы и у геймифицированного учебника harness устроен **одинаково**, но **наполнен** совсем по-разному.

- **Это не код продукта.** Harness живёт **в репозитории**, рядом с кодом, под контролем версий — но это не сам продукт. Это инструментальный слой над ним.

- **Это не бесплатно.** Построение harness — инвестиция (см. Часть 1). Сопровождение — продолжающаяся стоимость. Окупается на средних-длинных горизонтах.

## Главный месседж этой части

> **Harness — это общий слой над baseline возможностями AI-инструментов. Он содержит то, что инструменты не дают сами: знание организации о её продукте.**

Без него команда работает в режиме «AI знает синтаксис, не знает наш контекст».
С ним — AI работает на накопленном контексте организации.

Именно через harness реализуется главный приём из Части 1 — **спека как точка контроля**: спека хранится в harness, AI читает harness для генерации, проверка на выходе сверяет код со спекой из harness.
