# Пример — как могут выглядеть Task Types для разработки на 1С

> Четвёртый пример (после webmobile SaaS, payment gateway, FX trading core). Принципиально другой класс разработки — на платформе 1С:Предприятие, где **метаданные первичны над кодом**, **типовая конфигурация диктует архитектуру**, и **обновления от вендора регулярны**.
>
> Цель — показать, что Task Type работает и в low-code/platform-driven контексте, который сильно отличается от mainstream разработки.
>
> Я выбрал 1С (а не SAP) по двум причинам: релевантность российскому контексту и менее покрытость в индустриальных описаниях, что делает пример более ценным.
>
> Читается за 20 минут.

---

## 1. Контекст продукта

Возьмём типичный enterprise-проект на 1С — внедрение и доработка типовой конфигурации (например, «1С:ERP 2.5» или «1С:Управление торговлей 11») для среднего/крупного бизнеса.

**Технологический контекст**:
- **Платформа**: 1С:Предприятие 8.3 — proprietary платформа от компании 1С
- **Конфигурация**: «типовая» от вендора (1С:ERP, УТ, Розница и т.д.) + наши доработки
- **Язык разработки**: встроенный язык 1С (русский синтаксис, специфический)
- **Метаданные**: справочники, документы, регистры (накопления, сведений, расчёта), отчёты, обработки — это **первичные сущности конфигурации**
- **UI**: автогенерируемые формы платформой; ручная кастомизация — отдельная работа
- **Хранилище кода**: исторически — внутренний механизм 1С (хранилище конфигурации). Сейчас — Git через EDT, но многие команды до сих пор по-старому.
- **Тестирование**: исторически слабое (ручное), но vanessa-add-on, тестирование через сценарии — появляется
- **Релизы**: через `cf`/`cfu` файлы, обновление конфигурации в проде с реструктуризацией БД

**Главные отличия от других доменов**:
- **Метаданные первичны**. Большая часть «архитектуры» — это объекты конфигурации, не код. Код (модули) живёт *вокруг* объектов.
- **Типовая + доработки** — постоянная диалектика. Каждый раз когда вендор выпускает новую версию типовой, доработки нужно адаптировать.
- **Регуляторика течёт через вендора**. Налоги, формы отчётности, законодательные изменения приходят патчами от 1С. Это не нашa работа их разрабатывать — но интегрировать с нашими изменениями нужно.
- **Auto-generated UI**. Большинство форм генерируются платформой по метаданным. Это и плюс (быстро), и минус (кастомизация — отдельная boll).
- **Слабая testability** (исторически). Хотя меняется — но не так как в обычной разработке.
- **Бухгалтерская / учётная природа**. Большая часть доработок — про регистры учёта, движения, проводки, отчётность.

---

## 2. Что меняется в классификации задач для 1С-разработки

Те же три цели классификации (autonomy, gates, context), но особенности:

- **Autonomy ограничивается AI capability в 1С-стеке.** Современные AI значительно слабее в 1С-разработке, чем в JavaScript/Python — мало training данных, специфика языка, метаданная природа платформы. Практический потолок autonomy ниже.
- **Gates специфические**: проверка реструктуризации БД, проверка на конфликт с типовой, проверка прав доступа, проверка форм после автогенерации.
- **Context — это типовая конфигурация и стандарты разработки 1С.** «Стандарты разработки от 1С» — это несколько сотен страниц требований к коду. KB в org layer обязательно их инкорпорирует.

И ещё: **vendor update cycle** — это **отдельная активность**, которая в других доменах либо отсутствует, либо незначительна. Здесь — ключевая часть жизни проекта.

---

## 3. Схема Task Type — та же

Как и в предыдущих примерах:

```yaml
task_type:
  name
  detection: { triggers, file_signals }
  blast_radius: { users_affected, reversibility, cross_team }
  default_autonomy
  required_context
  required_gates
  typical_decomposition
```

Можно добавить домен-специфичные поля: `metadata_changes`, `restructuring_required`, `vendor_typical_impact`.

## 4. Каталог Task Types для 1С-разработки

12 типов, отражающих типичную работу.

### Type 1. Новый объект конфигурации

**Что**: добавление нового объекта — справочник, документ, регистр (накопления, сведений, бухгалтерии, расчёта), отчёт, обработка.

**Триггеры**: «нужен справочник для…», «новый документ…», «регистр учёта…», «новая форма движения».

**Метаданные**: новый объект в дереве конфигурации.

**Blast radius**: small-medium. Сам объект изолирован, но реструктуризация БД — это проперативно.

**Default autonomy**: **A2** (PR с review; AI генерирует структуру + базовый код модулей).

**Required gates**:
- Реструктуризация БД проходит без ошибок на staging
- Соответствие стандартам разработки 1С (наименование, структура реквизитов)
- Права доступа настроены (без открытых дыр)
- Корректность движений (если документ создаёт регистровые записи)

**Typical decomposition**: метаданные → форма → модуль объекта (events) → модуль менеджера (общие операции) → проводки/движения (если документ) → регистрационные данные → разрешения и роли.

---

### Type 2. Изменение существующего объекта

**Что**: добавление реквизитов в справочник, нового свойства в документ, новых измерений в регистр.

**Default autonomy**: **A2** (но осторожно — может потребоваться миграция данных).

**Required gates**:
- Миграция исторических данных — есть план или явно не нужна
- Обратная совместимость с существующим кодом (другие места, использующие объект)
- Реструктуризация без потери данных
- Обновление прав доступа на новые реквизиты

**Особенность**: добавить реквизит — на 5 минут. Понять что он не сломает 50 мест в коде, использующих этот объект — это самостоятельная исследовательская работа. AI может помочь искать места использования.

---

### Type 3. Разработка отчёта

**Что**: новый отчёт, обычно через систему компоновки данных (СКД).

**Default autonomy**: **A2** (СКД — специфическая декларативная штука; AI всё ещё не очень в этом).

**Required gates**:
- Корректность данных (проверка vs известный baseline)
- Производительность на реалистичных объёмах данных
- Права доступа (отчёт должен учитывать RLS)
- Корректность отображения на разных формах представления

**Особенность**: отчёты — самая частая задача в 1С-разработке. Большая часть времени уходит сюда.

---

### Type 4. Бизнес-процесс / документооборот

**Что**: изменения в маршрутизации документов, статусах, согласованиях. Например, новая стадия согласования заказа.

**Default autonomy**: **A1-A2** (затрагивает живые процессы пользователей).

**Required gates**:
- Корректность переходов состояний
- Совместимость с уже запущенными «в работе» документами (не сломать их)
- Уведомления / задачи направляются правильным пользователям
- Откат / отмена работают корректно

**Особенность**: бизнес-процессы в 1С реализуются разными механизмами (регистры, статусы, БизнесПроцесс/Задача — entity платформы). AI должен понимать **какой механизм используется в этой конкретной конфигурации**.

---

### Type 5. Интеграция изменений от вендора (regulatory / законодательное обновление)

**Что**: 1С выпустила обновление типовой с изменениями налогового законодательства, новыми формами отчётности или подобными regulatory изменениями. Нужно интегрировать в нашу доработанную конфигурацию.

**Триггеры**: новый релиз типовой от 1С с пометкой «изменения законодательства».

**Default autonomy**: **A1** (regulatory изменения — всегда под бухгалтерией / compliance).

**Required gates**:
- Сравнение типовой версия N+1 с N: что именно поменяли
- Конфликты с нашими доработками — выявлены и разрешены
- Тесты налоговой отчётности — проходят
- Бухгалтерия проверила корректность на тестовой базе

**Особенность**: тут две роли — разработчик 1С и **главбух / методолог**. Без последнего merge не done. Это **одна из самых частых работ** в 1С-командах.

---

### Type 6. Vendor update merge (мердж новой версии типовой)

**Что**: вышла новая major-версия типовой (например, ERP 2.4 → 2.5). Нужно адаптировать наши доработки.

**Default autonomy**: **A1** (это огромная и осторожная работа).

**Required gates**:
- Полное сравнение конфигураций
- Каждое расхождение — намеренное (не потерянное)
- Регрессионное тестирование критических процессов
- План отката
- Phased rollout (тестовая база → пилот → весь продакшн)

**Typical decomposition**: эта работа **сама декомпозируется на десятки work units** разных типов.

**Особенность**: единственный тип, который реально **может занимать месяцы**. Cross-cutting через всю конфигурацию.

---

### Type 7. Custom UI form / interface customization

**Что**: ручная доработка формы — нестандартная компоновка, динамическое поведение, валидация при вводе.

**Default autonomy**: **A2** (UI код в 1С специфичен; AI может, но требует review).

**Required gates**:
- Корректность отрисовки на разных режимах (тонкий клиент, веб-клиент, мобильный)
- События формы (при изменении, перед записью, и т.д.) — корректно
- Доступность функционала роли пользователя (RLS работает)

**Особенность**: web-клиент и mobile-клиент 1С — отдельные платформенные runtime'ы с особенностями. Не всё, что работает в толстом клиенте, работает в web.

---

### Type 8. External integration (REST / SOAP / файлообмен)

**Что**: интеграция с внешними системами — CRM, маркетплейс, банк-клиент, ЭДО, госсервисы.

**Default autonomy**: **A2** (типовая работа, но требует тестирования с реальной системой).

**Required gates**:
- Контракт API закреплён (описание в KB)
- Обработка ошибок / retry / timeout
- Логирование обмена (для разбирательств)
- Аутентификация / авторизация настроена
- Тестовый контур существует

**Особенность**: 1С исторически интегрировалась через **обмены файлами**, потом через COM, сейчас — REST/SOAP/ws. Каждый старый протокол ещё может встречаться в legacy-системах.

---

### Type 9. Авторизация / роли / RLS

**Что**: изменение ролей доступа, ограничения на уровне записей (RLS — Row-Level Security в 1С).

**Default autonomy**: **A1** (security-чувствительно).

**Required gates**:
- Проверка по матрице «кто что должен видеть»
- Тестирование с реальными ролями (не от админа)
- Производительность с RLS — не упала (RLS дорогая операция)

**Особенность**: ошибки в правах = data leak. Поэтому low autonomy.

---

### Type 10. Performance optimization

**Что**: ускорение операций — обычно через индексы, переписывание запросов, изменение структуры регистров, кеширование.

**Default autonomy**: **A2** (но в hot path — ближе к A1).

**Required gates**:
- Профилирование до и после (Замер производительности 1С)
- Performance regression tests
- На реалистичных объёмах данных

**Особенность**: основная проблема производительности 1С — **большие регистры** (миллионы записей). Запросы к ним без правильных индексов — катастрофа.

---

### Type 11. Миграция / конвертация данных

**Что**: перенос данных из одной конфигурации в другую (например, с УТ 10.3 на ERP 2.5), либо разовая массовая обработка существующих данных.

**Default autonomy**: **A1** (необратимо при ошибке).

**Required gates**:
- Тестовая база: миграция прошла без потерь
- Контрольные точки: суммы остатков, количества документов совпадают
- План отката (восстановление из бэкапа)
- Phased: пилотная группа → остальные

**Особенность**: миграции — самые рискованные операции. Большинство «эпических факапов» в 1С-проектах — здесь.

---

### Type 12. Bug fix

**Что**: фикс бага. Может быть в типовой (тогда мы или ждём от вендора, или временно правим у себя) или в наших доработках.

**Default autonomy**: **A2** (но критичные баги — ближе к Type 12 webmobile, hotfix).

**Required gates**:
- Воспроизведение бага на staging
- Regression test (конкретно для этого бага)
- Не сломал что-то ещё (что трогает тот же объект)

**Особенность**: баги в типовой — отдельная категория, потому что фиксить в типовой = создавать **наше расхождение с вендором**, что усложняет следующий vendor update merge. Часто лучше подождать патч от 1С, обходя баг временно.

## 5. Worked example — переход с УТ 10.3 на ERP 2.5

Реалистичная задача:

> «Компания работает на 1С:Управление торговлей 10.3 уже 8 лет. Накопилось много доработок, типовая давно не обновлялась. Бизнес растёт — нужен полноценный финансовый учёт, бюджетирование, расширенная аналитика. Решение — переход на 1С:ERP 2.5».

Это **проект на 6-12 месяцев**, не задача. Но даже на верхнем уровне видна декомпозиция:

| # | Work unit | Type | Зависимости | Default autonomy |
|---|---|---|---|---|
| 1 | Аудит существующих доработок: что переносить | (analysis) | — | manual |
| 2 | Установка ERP 2.5 на тестовый контур | (setup) | — | manual |
| 3 | Миграция мастер-данных (контрагенты, номенклатура) | Type 11 (migration) | depends on #2 | A1 |
| 4 | Миграция остатков и товаров | Type 11 (migration) | depends on #3 | A1 |
| 5 | Перенос наших доработок справочников и документов | Type 1, 2 (objects) | depends on #1, #2 | A2 |
| 6 | Перенос наших отчётов | Type 3 (reports) | depends on #5 | A2 |
| 7 | Перенос интеграций с внешними системами | Type 8 (integration) | depends on #5 | A2 |
| 8 | Адаптация ролей и прав доступа | Type 9 (auth) | depends on #5 | A1 |
| 9 | Custom UI формы (то что было кастомизировано) | Type 7 (UI) | depends on #5 | A2 |
| 10 | Бизнес-процессы: переадаптация | Type 4 (BP) | depends on #5, #8 | A1 |
| 11 | Performance тестирование на реалистичных данных | Type 10 (perf) | depends on #3-#10 | A2 |
| 12 | User Acceptance Testing с бухгалтерией | (testing) | depends on #1-#11 | manual |
| 13 | План phased rollout: пилот, затем все департаменты | (process) | depends on #12 | manual |
| 14 | Cutover (момент перехода) | (operation) | depends on #13 | manual |
| 15 | Постпереходная поддержка и закрытие финальных багов | Type 12 (bugfix) | depends on #14 | A2 |

Видно сразу:
- **Большая часть на A1 или manual** — миграции необратимы, ошибка стоит дорого
- **Работа идёт параллельно** во многих фронтах после первичной миграции
- **UAT с бухгалтерией** — критическая роль, не разработческая
- **Cutover** — отдельная операционная активность с минутной точностью planning'а
- **Project takes 6+ months**, не sprint

Этот тип проекта — **самый большой класс работ** в enterprise 1С разработке. Часто это и есть весь проект.

## 6. Что становится видно

**(1) Метаданные диктуют структуру.** Большинство типов начинаются с изменений конфигурации (метаданных), а код пишется вокруг. Это *обратно* mainstream разработке, где первичен код.

**(2) Vendor update cycle — first-class concern.** Type 5 и 6 (regulatory updates и major version migrations) — это огромная часть работы 1С-команд. В webmobile, payment, FX trading — таких типов нет вообще или они незначительны.

**(3) Бухгалтерская / методологическая роль.** Главбух, методолог по учёту — обязательные участники почти каждого regulatory work unit. Это не «business stakeholder» в обычном смысле, это **technical co-developer** в понимании какие проводки правильны.

**(4) AI capability в 1С — слабая.** GPT/Claude знает 1С хуже чем JavaScript на порядки. Поэтому autonomy дефолтно ниже, и **много reliance на developer expertise**. AI помогает, но финальный код часто пишет человек.

**(5) Auto-generated UI и кастомизация UI — два разных класса работ.** Большинство форм платформа делает сама. Кастомные формы — отдельный тип (Type 7).

**(6) Низкая testability — известная проблема домена.** Большинство 1С-команд не имеют unit-тестов. Регрессия — через UAT. Это **системное ограничение**, и methodology должна это recognize.

**(7) Миграции данных — самый рискованный класс работ.** Type 11 — здесь концентрация катастрофических ошибок.

## 7. Что не fits классификацию

**Кейс 1: «Закрытие месяца»** — это операционная активность бухгалтерии, не разработческая. Но иногда требует фиксов от разработчиков (если что-то сломалось). Тут смешивается операционка и разработка.

**Кейс 2: «Подготовка к налоговой проверке»** — может потребовать регенерации отчётов, восстановления данных, пересчётов. Не вписывается в обычные task types.

**Кейс 3: «Переход на новую платформу 8.4»** — раз в несколько лет. Затрагивает каждый объект конфигурации. Это **архитектурная мегазадача**, аналог Type 6 (vendor update merge), но на уровне платформы, а не конфигурации.

**Кейс 4: «Внешний аудит конфигурации»** — компания нанимает аудитора для проверки кода и архитектуры. Output — список рекомендаций. Это не задача в обычном смысле.

## 8. Что отличается от других трёх примеров

Расширение сравнительной таблицы:

| | Webmobile | Payment Gateway | FX Trading | 1С Development |
|---|---|---|---|---|
| Главный stake | UX | Money correctness | Latency, money | Учётная корректность, regulatory compliance |
| Доминирующий A-уровень | A2-A3 | A1-A2 | A1 | A1-A2 (с upper limit от AI capability) |
| Stack profile | Modern | Backend SaaS | Native low-level | Proprietary platform (1С) |
| AI capability | High | Medium | Low (hot path) | **Low** (мало training data) |
| Первичный артефакт разработки | Код | Код + конфиги | Код + event log | **Метаданные** (объекты конфигурации) |
| UI | Big component | Минимум | Минимум | Auto-generated по умолчанию |
| Тестирование | Стандартное | Расширенное (PCI) | Backtesting + replay | Слабое (UAT-driven) |
| Vendor relationship | Опциональные интеграции | Multi-provider integration | Multi-venue connectivity | **Vendor (1С) диктует архитектуру** + regulatory updates от вендора |
| Major upgrade frequency | Continuous | Continuous | Continuous | **Раз в годы** (новая major типовой) — and it's a project |
| Бухгалтерская / методологическая роль | Нет | Есть (financial) | Есть (quants) | **Обязательна** в каждом learning-related изменении |
| Тестовый контур | CI/CD | Sandbox от провайдера | Backtesting infra | Тестовая база с production data subset |
| Default cycle time | Часы-дни | Дни-недели | Недели-месяцы | Дни-месяцы (перенос — месяцы) |

**Главный наблюдение**: 1С — это **не «backend разработка с местным колоритом»**. Это **отдельный мир разработки**, где даже понятие «код» устроено иначе — потому что метаданные первичны.

Каталоги типов между mainstream разработкой и 1С пересекаются **минимально**. Из 12 webmobile типов — ни один не работает в 1С 1-в-1. Адаптируются — частично — performance optimization, integration, role/permission. Остальные — специфичны.

## 9. Что это значит для методики

**(1) Concept «AI-restricted zones»** актуален не только для FX trading hot path, но и для 1С (где AI слабее в принципе). Methodology должна явно recognize, что в некоторых доменах **дефолтный потолок autonomy ниже из-за AI capability gap**.

**(2) Vendor relationship как axis.** Domains с сильной vendor зависимостью (1С) или multi-vendor integration (payment gateway) требуют **специального типа задач** для управления вендорным циклом. Это в существующих task types не было — теперь видим что нужно.

**(3) Метаданные vs код — отдельный аспект архитектуры.** Low-code / metadata-driven платформы (1С, Mendix, OutSystems) требуют другого подхода к classification. Code-only platforms (webmobile, payment, FX) проще.

**(4) Бухгалтерская / методологическая роль** — не специфика 1С. В payment gateway это compliance officer. В FX — quants / risk team. Methodology должна явно recognize **role beyond the dev team** в gates.

**(5) Тестирование — не universal practice.** В 1С культура unit-testing слабая, регрессия — через UAT. Methodology не должна жёстко требовать «обязательный test coverage» — гибкость нужна.

**(6) Major upgrade as project, not task.** В большинстве доменов upgrade непрерывный. В 1С (и SAP, и других enterprise platforms) major upgrade — это **отдельный проект квартала / года**. Methodology должна это поддерживать.

## 10. Открытые вопросы (специфичные для 1С)

**1. Как methodology относится к платформам с слабой AI поддержкой?** 1С, ABAP (SAP), некоторые специализированные DSL — здесь AI capability существенно ниже. Methodology должна давать рекомендации «что делать» в этой ситуации.

**2. Vendor update workflow** — как структурировать его в KB, как поддерживать «карту наших расхождений с типовой»?

**3. Metadata-driven artifacts в KB** — как описывать паттерны метаданных (структура справочника, схема регистра) в KB? Это не код, это структурированная сущность.

**4. UAT-driven QA** — methodology поддерживает или предпочитает unit-driven testing? В каком-то домене UAT — единственный реалистичный путь.

## 11. Главный месседж после четырёх примеров

После четырёх **сильно разных** примеров (webmobile, payment, FX trading, 1С) однозначно подтверждается:

**Methodology — schema, не каталог.** Каталоги типов в этих доменах **практически не пересекаются**. Schema того, *как описывается тип*, **совершенно одна и та же**.

Любая попытка дать «универсальный список из 50 task types для всех» — обречена. Будет либо:
- Generic до бесполезности
- Biased под один домен (и не работает в других)

Правильный путь:
- Schema universal
- Каталог — domain-specific, наполняется в каждой организации
- Примеры из разных доменов — как калибровочный материал
- Methodology предоставляет инструменты для построения каталога, не сам каталог

Это и есть наша A57: **task types — domain content**.
